The correct data model

This is the clean mental model:

Question Library
Reusable master questions

Workbook Templates
Reusable workbook structures made from library questions

Project Workbooks
A copied instance of a workbook template attached to one project

Contributor Assignments
Which contributors can answer which project workbooks

Workbook Responses
Answers submitted by contributors

That separation is important.

Otherwise, one day you edit the “Tech Stack” workbook for Magnisol and accidentally change the default workbook for every future project. That is how innocent systems become haunted.

What I’d tell Replit next

Use this prompt:

We need to refactor the workbook UX architecture. The workbook builder and question library should not live inside the project discovery page. The project page should only show workbooks attached to that specific project.

Please implement a cleaner separation between global workbook tools and project workbook instances.

Context:
Deploy OS uses workbooks to collect structured discovery input from contributors and clients. Workbooks should be reusable across projects, but once added to a project they become project-specific instances that can be edited without changing the source template.

Current issue:
The Discovery tab on the project page is overloaded. It currently contains workbook creation, question library selection, workbook editing, contributor context, and project discovery progress. This makes the project page confusing and too dense.

9. Data model guidance
Use this conceptual structure if existing models allow it:

- LibraryQuestion: reusable master question
- WorkbookTemplate: reusable workbook structure
- WorkbookTemplateSection: sections inside templates
- WorkbookTemplateQuestion: questions linked to template sections
- ProjectWorkbook: project-specific workbook instance
- ProjectWorkbookSection: copied section for a project
- ProjectWorkbookQuestion: copied question for a project
- WorkbookResponse: contributor/client answer

If the current schema uses DiscoveryEvidence for workbooks, do not break existing data. Add a migration or compatibility layer if needed.

The big decision

You should stop treating “workbooks” as a project feature.

They are a platform capability.

Projects consume workbooks.
Projects do not own the workbook system.

That one shift will make the whole thing cleaner.
